# Фреймворк для разработки с участием AI агента разработки

## Цель проекта
Разработчик должен мочь эффективно и безопасно подключать AI агента разработки к работе над своими текущими задачами, чтобы делать их быстрее

## Рамки проекта
- Мы подразумеваем что процесс разработки с участием AI агента отличается от процесса разработки без агента незначительно. Агент в этом процессе берет на себя рутину, но все ответственные решения остаются за разработчиком, который вовлечен в процесс на всем протяжении разработки
- Мы не строим фреймворк для выполнения множества задач параллельно, т.к. это значительно отличается от обычного процесса разработки
- Мы не строим фреймворк для вайб-кодинга, где AI агент разработки полностью берет на себя всю работу и возвращает уже готовый результат

## Ключевые принципы
1. opensource - не полагаемся на проприетарные решения
2. неинвазивность в кодовой базе - о подключении AI агента разработки к проекту знает только разработчик. Поведение должно быть аналогично подключению к проекту IDE: разные люди должны мочь спокойно работать над одним проектом в разных IDE и даже не догадываться, что работают в разных IDE - никаких следов или привязок к конкретным инструментам в кодовой базе нет
3. безопасность - окружение, в котором работает AI агент разработки, изолировано от хоста нативными инструментами - доступ к файлам, расположенным вне текущего проекта, жестко регламентирован. Никакие файлы с секретами агенту недоступны - все, что должно быть ему доступно он получает из конфигурационных файлов и env-переменных
4. прозрачность - все окружение агента прозрачно для разработчика. он может видеть все слои переопределения конфигурации
5. воспроизводимость - конфигурации всех уровней должны быть под контролем версий

## Архитектура
Окружение для агента формируется из нескольких уровней:
### 1. Уровень профиля разработчика
Глобальные настройки обнаруживаются автоматически по фиксированным путям:
- `~/.config/opencode` - конфигурация
- `~/.local/share/opencode/auth.json` - файл аутентификации

Здесь находятся элементы, которые логично переиспользовать между всеми проектами:
- black- и white- списки провайдеров
- базовая конфигурация провайдеров - урлы, модели

Фреймворк не спрашивает пользователя о расположении или создании глобальных настроек.
Конфигурация этого уровня не может изменяться агентом - ей управляет только разработчик вне работы над проектом
Конфигурация этого уровня считается стабильной - может быть под контролем версий или не быть
При изменении файлов этого уровня - все настроенные на использование фреймворка проекты должны увидеть изменения

### 2. Уровень фреймворка
Здесь находятся элементы, которые тоже переиспользуются между проектами, но уже определяют каркас стандартного использования AI агента разработки:
- настройки средств изоляции - контейнеризации и т.п.
  - настройки контейнера: версии ОС, доступные утилиты и инструменты
  - настройка окружения - пользователь, от имени которого будет работать агент 
  - пути, доступные для чтения и записи, доступные утилиты
  - выбор агента разработки, его версии
- настройки агента
  - подключаемые по умолчанию плагины
  - настройки интерфейса агента
  - настройки по умолчанию: 
    - модели для служебных агентов
    - пермишены
    - лимиты
- точки кастомизации конфигурации под проект. например, через переопределение переменных окружения

Конфигурация этого уровня не может изменяться агентом - она управляется через систему контроля версий, независимо от проектов разработки
При изменении файлов этого уровня - все настроенные на использование фреймворка проекты должны увидеть изменения

### Уровень проекта
Здесь находятся элементы, которые индивидуальны для каждого проекта:
- настройки окружения кастомизации конфигурации фреймворка под конкретный проект
- настройки AI агента разработки
  - настройки агентов
  - mcp-сервера
  - скилы
  - инструменты

Конфигурация этого уровня тоже не может изменяться агентом - только разработчиком вне сессии агента разработки. Но эта конфигурация должна быть под контролем версий, связанным с данным проектом
При изменении файлов этого уровня - изменения применятся только к текущему проекту

## Концепция использования фреймворка

### Первичная настройка фреймворка
1. Клонирование репозитория фреймворка к себе
2. Добавление скрипта настройки проекта, который содержится в репозитории фреймворка наряду с шаблонами конфигурации в PATH через инструмент вроде pipx, который может запускать скрипт в правильном окружении

### Первичная настройка проекта
1. Переход в проект, к которому хотим подключить AI агента разработки, вызов настроечного скрипта, который подготовит проект к использованию фреймворка: настройка контроля версий, подключение конфигурации и настроек всех уровней, контейнеров, окружений и т.п.
2. Запуск AI агента разработки, сконфигурированного в проекте

### Донастройка фреймворка
1. Обновление репозитория фреймворка. Изменения шаблонов конфигурации подхватят сразу все скофнигурированные проекты 

### Повторная настройка уже сконфигурированного проекта
1. Переход в проект, вызов настроечного скрипта, который подготовит проект к использованию AI агента разработки: очистит текущую конфигурацию фреймворка на проекте и сформирует новую

## Предлагаемый технологический стек
1. git - клонирование и обновление репозитория проекта, worktree - создание отдельной ветки в репозитории проекта для хранения конфигурации фреймворка в проекте
2. python, pipx - для скрипта настройки проекта
3. docker - как инструмент изоляции окружения и как инструмент, который должен быть доступен в окружении агента(DinD)
4. devcontainer-cli - для настройки изоляции
5. opencode - как движок агента разработки

## Development Setup

### Requirements
- Python 3.12+
- Poetry 2.0+

### Install

```bash
# Install Poetry (if not already installed)
pipx install poetry

# Clone the repository
git clone <repository-url>
cd opencode-framework

# Install dependencies
poetry install
```

### Run Tests

```bash
poetry run pytest
```

### Run CLI

```bash
poetry run ocframework --version
```

### Build

```bash
poetry build
```
